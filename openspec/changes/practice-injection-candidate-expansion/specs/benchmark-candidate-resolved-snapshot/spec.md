## MODIFIED Requirements

### Requirement: Resolved Workspace Snapshot

Each kernel-backed candidate or task MUST have a committed resolved snapshot
that binds its immutable core version and hash, profile declaration,
materializer_kind, declared input (source + lockfile + manifest) hashes and
materialized public task/starter hashes. An `injection-calibration/v1`
candidate MUST additionally bind a profile-input hash over its private
condition metadata, declared Practice identifiers and hashes, irrelevant-control
measurement declaration, and decision rule. Snapshot verification MUST fail
when any bound source input, profile input, or resolved public output changes.
The snapshot MUST NOT contain Practice text or private Practice paths, and it
MUST NOT be regenerated by re-resolving a frozen historical revision.

#### Scenario: Private Practice declaration changes
- **WHEN** a kernel-backed Practice candidate's conditions metadata or declared
  Practice hash changes after its resolved snapshot is generated
- **THEN** snapshot verification fails until the candidate snapshot is
  regenerated and reviewed
- **AND THEN** the snapshot exposes no Practice text or private path

#### Scenario: Core source changes after snapshot generation
- **WHEN** a kernel-backed candidate's declared core changes after its resolved
  snapshot is generated
- **THEN** snapshot verification fails until the candidate snapshot is
  regenerated and reviewed

#### Scenario: Frozen revision is not re-resolved
- **WHEN** a frozen Skill task revision exists with a historical snapshot
- **THEN** the kernel MUST NOT rewrite or re-resolve that historical snapshot
- **AND THEN** only future new revisions may declare a kernel block

### Requirement: Generated Output Is Excluded

Resolved snapshot verification MUST exclude installed dependencies, build
output, browser test output, run workspaces, logs and evidence indexes while
retaining all source inputs needed to reproduce the resolved public input. The
repository starter directory MUST NOT contain `node_modules/`, `dist/`,
`test-results/`, or other generated output; these MUST be produced by
materialization.

#### Scenario: Build output is present during snapshot verification
- **WHEN** a maintainer has installed dependencies or built a candidate locally
- **THEN** snapshot verification remains determined by committed core and
  candidate source rather than generated output

#### Scenario: Generated output is committed in a starter
- **WHEN** a starter directory contains `node_modules/`, `dist/`, or
  `test-results/`
- **THEN** validation rejects the starter until generated output is removed
