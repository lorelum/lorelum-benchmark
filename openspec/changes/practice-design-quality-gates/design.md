## 背景

#75 的登录页 candidate 已完成一次本地 Oracle 对照。最终的有效批次表明，相关 React API 分层 Practice 在两次运行中均同时满足登录语义和分层质量信号，而 baseline 与无关对照只满足登录语义。该结果成立前，候选经历了两类设计修正：一是将 Practice 从特定组件、文件路径和 helper 名称改为可迁移的适用场景、建议与 anti-pattern；二是将 probe 从 reference 结构匹配改为职责边界检查，并用 reference、职责等价实现和已知绕过校准。

这次经历揭示了跨 candidate 的缺口。公开任务、注入 Practice、私有语义验收和私有质量信号目前没有一个仓库级的作者指南来界定各自的职责，容易让未来实现把隐藏 reference 写法当成任务要求，或把质量信号错误地并入任务完成状态。

本 change 只设计并落库维护者指南，拟新增 `docs/PRACTICE_BENCHMARK_GUIDE.md`，并从 `docs/BENCHMARK_PROTOCOL.md` 链接到该指南。它不改写 #75 candidate、不会为 Practice 定义机器检查 DSL，也不触发模型调用或正式记录。

## 目标与非目标

**目标：**

- 以可执行的分类规则区分公开任务信息、可迁移 Practice、私有语义验收、私有质量信号和实现偏好。
- 定义硬门槛与软质量信号的不同后果：任务语义、公开接口、隔离与生命周期失败可以使任务失败；质量信号单独报告，不将代码局部写法伪装成任务失败。
- 定义何时特定路径、导出或命名可以成为合同：只有它已在公开任务或稳定外部接口中被声明且对可观察行为不可替代时。
- 固定质量 probe 的离线校准和结果报告最小要求，使 future candidate 能接受职责等价实现、拒绝已声明反模式，并以人可读原始次数解释结果。

**非目标：**

- 不重跑、修改或提升 #75 的 candidate，也不将它的两次本地结果升级为正式 benchmark 结论。
- 不修改共享 runner、schema、formal environment、正式 suite 或 `results/records/`。
- 不把 Practice 变成 lint 规则、权重总分或强制统一架构风格的机制。
- 不在本 change 中解决跨框架静态分析的通用实现；各 candidate 仍可选择适合其技术栈的私有质量 probe。

## 决策

### 1. 以五类信息分离设计责任

维护者指南把任何候选材料归入以下五类：

| 类别 | 可见性与职责 | 是否可决定任务完成 |
| --- | --- | --- |
| 公开任务行为 | `public/` 题面与公开测试中的用户可观察结果、已声明公共接口 | 可以 |
| 注入 Practice | 私有、版本化的通用工程指导：适用场景、建议、理由、anti-pattern | 不单独决定 |
| 私有语义验收 | 对公开任务行为的自动验证 | 可以 |
| 私有质量信号 | 与 Practice 有关、可观察且允许职责等价实现的代码质量证据 | 不可以，单独报告 |
| 实现偏好 | reference 的文件路径、局部 helper、命名、格式或无外部影响的布局 | 不可以 |

选择这个分类而不是“所有 private assertion 都是硬门槛”，因为 #75 已证明同一职责可由异常或判别式领域结果、不同模块路径和不同命名实现。把这些差异当失败会测量对 reference 的猜测，而非 Practice 的利用。

### 2. Practice 只传达可迁移指导，不补全单题解法

Practice 卡必须包含稳定标识、标题、阶段、技术栈、适用场景和自然语言指导；正文使用建议与 anti-pattern 说明职责边界和原因。它可以指定领域边界，例如“组件不直接处理 transport”，但不得以一个未公开的 candidate 文件路径、函数名、helper 拆分或 reference 代码作为达标条件。

若特定路径、导出或协议确实属于产品集成合同，维护者必须将其作为公开任务接口或稳定的可观察约束声明；此时它不是由 Practice 私下补充的要求。选择该规则可保持 baseline 的公开输入不变，同时允许对真正的兼容性合同进行严格验收。

### 3. 质量信号可判定，但不与任务完成混淆

质量 probe 可以返回 pass/fail 或原始子信号，以支持条件比较；它必须与 Practice 中的建议或 anti-pattern 有可解释映射，并接受职责等价实现。语义测试与质量 probe 分别记录：语义失败即任务失败；质量失败在语义通过时只表明未观察到对应的 Practice 相关质量，不得将该尝试描述为功能失败。

这比加权总分更适合候选阶段。总分会掩盖“功能正确但质量信号缺失”或“质量信号出现但功能错误”的不同原因，也会在任务集尚未稳定时过早冻结权重。

### 4. 运行前校准防止 probe 把实现偏好伪装成质量

每个 candidate 的私有质量 probe 必须在模型运行前验证三类固定样例：满足职责的 reference、以不同命名或局部布局实现同一职责的等价样例、以及至少一个对应 anti-pattern 或已知绕过。前两者必须通过，绕过必须失败。若无法为某项断言构造等价实现，维护者必须把该断言降为报告性证据或将其提升为公开合同并解释原因。

这比在真实模型输出后调节 evaluator 更可靠，也使 probe 的强度可在运行前被审阅。

### 5. 结果以人可读原始维度表达

每个本地或候选对照结果必须以条件、注入内容、每条件运行次数、语义通过次数、质量信号通过次数和两者同时通过次数呈现；每个分数必须解释分子、分母和通过含义。结论只能描述已运行的 candidate、Practice 和模型条件，不得把两次本地对照表述为 retrieval、产品或泛化能力证明。

## 风险与取舍

- **质量边界仍需维护者判断** → 指南要求将 Practice 建议、probe 信号和反模式的映射写入 candidate 设计，并在模型运行前校准。
- **不同技术栈难以共用同一静态分析器** → 固定的是职责与校准要求，不固定 AST、浏览器测试或其他 probe 实现。
- **更宽松的等价实现可能漏检某些风格偏好** → 将偏好作为报告性代码审查信息；只有公开集成合同才升级为硬门槛。
- **小样本容易被误读** → 结果只保留原始次数和方向性措辞，禁止由候选运行推导产品结论。

## 迁移计划

1. 在同一 change 的实施阶段新增维护者指南，并从 benchmark 协议链接到它。
2. 任何新 Practice candidate 在设计阶段按指南填写信息分类、Practice/anti-pattern 映射、硬门槛和质量信号、校准样例及结果表模板。
3. 对已有 candidate 的代码或 evaluator 变更另建可追溯 issue 与 OpenSpec change；冻结 revision 必须创建下一版本，不在本 change 中回写。

回滚只需移除新增指南和协议链接；不涉及 runtime、snapshot、record 或已冻结输入。

## 待确认问题

- benchmark 是否直接采用 Lorelum Practice 的完整 frontmatter，或由 treatment manifest 映射等价字段，将在实际引入 retrieval 或共享 treatment 时单独决定。
- 哪些质量信号需要人工补充审阅而非自动 probe，取决于后续 candidate 的技术栈和可观察边界；本指南不把人工审阅设为当前小试的前置条件。
